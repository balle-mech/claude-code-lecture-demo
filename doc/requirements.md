# TODOアプリ 要件定義(EARS 記法)

## このドキュメントについて

- 要件は EARS 記法で記述する(パターンの定義は `.claude/rules/development-process.md` を参照)
- 各要件は一意のIDを持ち、設計(design.md)・テストと要件IDでひも付ける(トレーサビリティ)
- IDの命名: `REQ-<機能略称>-<連番>`。削除したIDは再利用しない

## 目的

研修「Claude Code入門」の登壇者が、AI駆動開発フローを事前に体験するための学習用アプリ。
**研修本番では使用しない。**

## 技術構成

- HTML + CSS + JavaScript(フレームワークなし)
- ロジックは純粋関数として `src/logic.js` に分離し `node:test` でテストする
- ローカル実行: VSCode Live Server / データ永続化: localStorage

## Step 1: 最小構成

### タスク追加(ADD)

| ID          | パターン | 要件                                                                                                                                                      |
| ----------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| REQ-ADD-001 | Event    | ユーザーが追加操作(追加ボタン押下または Enter キー)を行ったとき、システムは入力されたテキストを未完了状態のタスクとして一覧の末尾に追加しなければならない |
| REQ-ADD-002 | Event    | タスクが追加されたとき、システムは入力欄を空にしなければならない                                                                                          |
| REQ-ADD-003 | Unwanted | もし入力が空文字または空白のみならば、システムはタスクを追加してはならない                                                                                |

### タスク完了(DONE)

| ID           | パターン | 要件                                                                                                       |
| ------------ | -------- | ---------------------------------------------------------------------------------------------------------- |
| REQ-DONE-001 | Event    | ユーザーがタスクのチェックボックスを操作したとき、システムはそのタスクの完了状態を切り替えなければならない |
| REQ-DONE-002 | State    | タスクが完了状態の間、システムはそのタスクのテキストを取り消し線付きで表示しなければならない               |

### タスク削除(DEL)

| ID          | パターン | 要件                                                                                             |
| ----------- | -------- | ------------------------------------------------------------------------------------------------ |
| REQ-DEL-001 | Event    | ユーザーがタスクの削除ボタンを押下したとき、システムはそのタスクを一覧から削除しなければならない |

### 永続化(SAVE)

| ID           | パターン | 要件                                                                                                               |
| ------------ | -------- | ------------------------------------------------------------------------------------------------------------------ |
| REQ-SAVE-001 | Event    | タスクの追加・完了状態の切り替え・削除が行われたとき、システムはタスク一覧を localStorage に保存しなければならない |
| REQ-SAVE-002 | Event    | ページが読み込まれたとき、システムは localStorage からタスク一覧を復元して表示しなければならない                   |
| REQ-SAVE-003 | Unwanted | もし localStorage のデータが存在しないか不正ならば、システムは空のタスク一覧として起動しなければならない           |

## Step 2: 期限・優先度(ドラフト・未承認)

| ID          | パターン   | 要件                                                                                 |
| ----------- | ---------- | ------------------------------------------------------------------------------------ |
| REQ-DUE-001 | Ubiquitous | システムはタスクに期限日を設定できなければならない                                   |
| REQ-DUE-002 | State      | タスクに期限日が設定されている間、システムは一覧にその期限日を表示しなければならない |
| REQ-PRI-001 | Ubiquitous | システムはタスクに優先度(高/中/低)を設定できなければならない                         |
| REQ-PRI-002 | Unwanted   | もし優先度が指定されなければ、システムは優先度を「中」としなければならない           |

## Step 3: フィルタ・並び替え(ドラフト・未承認)

| ID          | パターン | 要件                                                                                                             |
| ----------- | -------- | ---------------------------------------------------------------------------------------------------------------- |
| REQ-FLT-001 | Event    | ユーザーがフィルタ(全部/未完了/完了)を選択したとき、システムは該当する状態のタスクのみを表示しなければならない   |
| REQ-SRT-001 | Event    | ユーザーが期限順の並び替えを選択したとき、システムはタスクを期限日の昇順(期限なしは末尾)で表示しなければならない |
| REQ-SRT-002 | Event    | ユーザーが優先度順の並び替えを選択したとき、システムはタスクを優先度の高い順で表示しなければならない             |

## Step 4: 検証項目(研修デモ機能の事前検証)

- サブエージェントでのテスト実行
- Playwright MCP による受け入れ確認
- skills の検証

## トレーサビリティ

- 設計: `doc/design.md` の各設計項目に要件IDを明記する
- ユニットテスト: テスト名に要件IDを含める(例: `test("REQ-ADD-001: ...")`)
- 受け入れ確認: Playwright MCP の確認結果を要件ID単位で報告する
