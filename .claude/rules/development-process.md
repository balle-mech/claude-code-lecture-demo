# 開発プロセスルール

このプロジェクト(TODOアプリ)の開発は **AI-DLC・スペック駆動開発** で進める。
コードより先に仕様(スペック)を確定させ、仕様を唯一の正として設計・テスト・実装を導出する。

## スペック駆動開発のフロー

各 Step(反復単位)ごとに以下の順で進める。

1. **要件定義**: `doc/requirements.md` に EARS 記法で要件を記述し、ユーザーとすり合わせて承認を得る
2. **設計**: `doc/design.md` に要件を満たす設計を記述する(どの要件をどのモジュール/関数が満たすかを明記)
3. **テスト → 実装**: TDD(後述)で進める。テストは必ず要件IDにひも付ける
4. **受け入れ確認**: Playwright MCP でブラウザを操作し、UI要件を満たすことを確認する

## 要件定義ルール(EARS 記法)

自然言語の曖昧さを排除するため、要件は EARS(Easy Approach to Requirements Syntax)のいずれかのパターンで記述する。

| パターン | テンプレート |
|---|---|
| Ubiquitous(常時) | システムは〈機能〉しなければならない |
| Event-driven(イベント駆動) | 〈トリガー〉のとき、システムは〈応答〉しなければならない |
| State-driven(状態駆動) | 〈状態〉の間、システムは〈応答〉しなければならない |
| Unwanted behavior(望ましくない事象) | もし〈望ましくない条件〉ならば、システムは〈応答〉しなければならない |
| Optional(機能依存) | 〈機能〉を備える場合、システムは〈応答〉しなければならない |

- 要件は1文につき1要件とし、テスト可能(検証可能)な表現で書く
- 各要件に一意のIDを付与する(例: `REQ-ADD-001`)。IDは削除しても再利用しない

## トレーサビリティルール

要件 → 設計 → テストのひも付きを常に追跡可能にする。

- **設計**: design.md の各設計項目に、対応する要件IDを明記する
- **ユニットテスト**: テスト名(またはコメント)に要件IDを含める(例: `test("REQ-ADD-001: ...")`)
- **受け入れ確認**: MCP での確認結果を要件ID単位で報告する
- 要件を変更したら、対応する設計・テストも同じ変更内で更新する
- 対応するテストのない要件、対応する要件のないテストを作らない

## テスト戦略(2層構成)

- **ロジック層**: 追加/完了/削除/保存などのロジックは純粋関数として `src/logic.js` 相当に分離し、`node:test` でユニットテストする(TDD の対象)
- **UI層**: DOM 操作・表示は Playwright MCP による受け入れ確認で検証する(各 Step 完了時)

## テスト駆動開発(TDD)

### Red → Green → Refactor サイクル

1. **Red**: 失敗するテストを書く
2. **Green**: テストが通る最小限の実装をする
3. **Refactor**: テストが通ったままコードを整理する

### 運用ルール

- 機能を実装する前に、必ず失敗するテストを先に書く
- テストが通る最小限の実装に留め、先回りした実装をしない
- リファクタリング後は必ずテストを再実行し、通ることを確認する

## 段階的な開発

- 機能は一気に作らず、小さく反復して育てる(requirements.md の Step 単位)
- 各 Step の完了時に Live Server 上で動作確認する
